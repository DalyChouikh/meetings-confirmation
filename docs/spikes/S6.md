# S6 — Google Sheets and Drive API facts for M7

- **Date:** 2026-10-10
- **Question:** Do the Sheets/Drive behaviours M7 relies on hold against a real Google account: the Meeting filter box (slicer), colour rules on open-ended ranges and their order, text kept as typed, Drive `appProperties` tagging, trashed and deleted files, error shapes, and the payload size and time per tab (spec §8, §13)?
- **Status:** **PASS** with three design corrections (below).

## Method

- Google Cloud project `tapnshow`: Google Sheets API and Google Drive API enabled; `…/auth/drive.file` added under Data Access (listed as non-sensitive). **No billing account** is attached (Owner, 2026-10-10; spec §15).
- Loopback consent (`spikes/s6-sheets/auth.ts`) with the Owner's test account: `openid email drive.file`, `access_type=offline`, `prompt=consent select_account`, `include_granted_scopes=true`.
- Probes (`spikes/s6-sheets/probe.ts`, `probe2.ts`, `probe3.ts`, `probe4.ts`) print only statuses, sizes, times and Google's error reasons; the data is synthetic.
- Manual checks by the Owner in the probe spreadsheet, plus a second account with view-only access in a private window.
- Afterwards the probe files were deleted from Drive and the local token file removed.

## Results

### Consent and scopes
- Google's screen: "TapNShow wants additional access to your Google Account" / "When you allow this access, TapNShow will be able to" / "See, edit, create, and delete only the specific Google Drive files you use with this app." It also shows "This app hasn't been verified by Google." (the app is unverified because of `gmail.send`) and "TapNShow already has some access".
- With `include_granted_scopes=true` the returned token carried the account's earlier grant too: `gmail.send userinfo.email userinfo.profile openid drive.file`. This confirms the callback scope rule: a token returned for one purpose can hold the other purpose's scope, so a connection is revoked only when it holds neither.
- The first sign-in returned no refresh token (Google's reason was not captured); the second, identical one did. The connect flow already treats a missing refresh token as a failed connect.

### Drive tagging
- `files.create` of a spreadsheet with `appProperties` → 200; `files.list` with `appProperties has { key='tapnshow_create_key' and value='…' }` finds it with only `drive.file`. **Holds.**

### Text kept as typed
- `stringValue` keeps `=1+1`, `+33 6` and `'quoted` as text. **Holds.**

### Colour rules (conditional formats)
- Rules added over open-ended row ranges (no `endRowIndex`) are stored bound to the grid and **follow the row count**: after growing to 20,004 rows the ranges ended at 20,004; after shrinking to 29 and growing to 3,004 they ended at 3,004. Rows written later are coloured (rows 5, 6, 9,000 and 9,001 checked through `effectiveFormat`). **Holds.**
- A cell matching two rules takes the rule with the **lowest index** (F6 matched both the tone rule at index 0 and the band rule at index 1 and shows the tone colour). So "first rule wins" by ascending index, as the plan's request builder assumes. **Holds; no swap.**
- Colours read back quantised to 8 bits (`0.73` → `0.7294118`).

### Meeting filter box (slicer)
- Owner check: picking one meeting in the filter box leaves only its rows visible **on the same tab**; a view-only person's choice hides rows for them only, while the Owner's window keeps its own choice. Column tints and the meeting bands show. **Holds.**
- **Correction 1:** a slicer created over an open-ended range is stored with the **row count at creation** (`endRowIndex` 10) and does **not** grow with the tab (still 10 after growing to 20,004). A second `addSlicer` over overlapping rows fails ("Two slicers can either have zero or all common rows").
- `addSlicer` accepts **our own `slicerId`**, and `updateSlicerSpec` with `fields: "dataRange"` moves the range to the exact last row (29 checked). So every redraw must set the slicer's `dataRange` to the tab's exact row count, using a slicer id we choose.

### Trashed and deleted files
- **Correction 2:** a write to a **trashed** file **succeeds** (200). Only Drive `files.get?fields=trashed` reports it (`"trashed": true`). The worker's `files.get` before writing is therefore the only trash detector (spec §8 already does this).
- (The plan's first trashed-write probe returned 400 because the probe wrote one column past the grid; that was the probe's bug, not Google's answer.)
- After a permanent Drive delete (204), Sheets kept answering 200 for a few seconds; after 15 s and 45 s both reads and writes returned **404 `NOT_FOUND`**. Drive `files.get` returned 404 at once.

### Error shapes
- An API not enabled for the project (Docs API): **403 `PERMISSION_DENIED`, reason `SERVICE_DISABLED`** (in the `ErrorInfo` details; newer APIs carry no `errors[].reason`). Older surfaces (Drive v3) report `accessNotConfigured` in `errors[].reason`, so the classifier checks both places.
- A token without the API's scope: **403 `PERMISSION_DENIED`, `insufficientPermissions` / `ACCESS_TOKEN_SCOPE_INSUFFICIENT`** → treated as lost access.
- Rate limits were not provoked (that would need about 60 writes a minute against the Owner's account). Documented by Google: Sheets answers 429 `RESOURCE_EXHAUSTED`; Drive reports `rateLimitExceeded` / `userRateLimitExceeded` as 403 or 429. The classifier maps them to retry.

### Payload size and time (one `batchUpdate` per tab)
Probe 1 (18 cells per row, every cell filled with short text):

| Rows | Bytes | Status | ms |
|---|---|---|---|
| 10,000 | 7,859,697 | 200 | 23,090 |
| 20,000 | 15,724,697 | 200 | 44,723 |

Probe 2 (realistic rows: the 15 visible columns + 3 helpers, empty cells as `{}`, plus the row-count and data-row format requests):

| Rows | Bytes | Status | ms |
|---|---|---|---|
| 2,000 | 1,640,684 | 200 | 5,099 |
| 2,500 | 2,051,423 | 200 | 6,594 / 6,630 |
| 3,000 | 2,462,036 | 200 | 7,780 |
| 4,000 | 3,283,432 | 200 | 9,777 |
| 5,000 | 4,105,784 | 200 | 12,508 / 12,192 |

- **Correction 3:** a realistic row is about **820 bytes**, not the 200 the spec estimated, and Google takes about **2.5 ms per row**. A 10,000-row tab is about 8 MB and 23 s.

## Decision

- **`SHEET_TAB_ROWS_MAX = 2_000`.** The plan's rule is "payload ≤ 2 MB (Google's recommended maximum) and time ≤ half the request timeout". Neither 10,000 (8 MB, 23 s) nor 5,000 (4.1 MB, 12.5 s) meets it, so the largest measured size that does is used: 2,000 rows (1.6 MB, 5.1 s; 2,500 is just over 2 MB). The club writes about 1,500 rows a year, so its years stay on one tab. The extreme case in the spec (100,000 rows a year) gets 50 tabs a year.
- **`SHEET_REQUEST_TIMEOUT_MS = 15_000`** (unchanged): a 2,000-row write takes about 5 s, a third of it.
- **Layout B stays** (the Meeting filter box works). Every redraw adds `updateSlicerSpec` (`fields: "dataRange"`) with the exact last row, and the slicer gets a deterministic id derived from the tab's sheet id, so the redraw never has to read it back.
- **Rule order:** tone rules at the lowest indexes, as planned (first rule by ascending index wins).
- **Trash detection:** `files.get?fields=trashed` before writing stays the only check; a `SERVICE_DISABLED` 403 is a "bug" (retry + Sentry), and an insufficient-scope 403 is lost access.
